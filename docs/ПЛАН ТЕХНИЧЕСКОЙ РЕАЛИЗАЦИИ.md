# Технический план реализации Token

Статус: рабочее ТЗ для разработки  
Дата: 2026-08-08  
Связанный документ: `docs/ТЕХНИЧЕСКОЕ ЗАДАНИЕ.md`

## 1. Назначение

Документ переводит целевое ТЗ в последовательность технических работ от
нынешнего прототипа до production-платформы. Каждый этап имеет зависимости,
результат, задачи, миграции, проверки и критерии завершения.

План рассчитан на старт до 200 пользователей. На первых этапах используется
модульный монолит с PostgreSQL. Redis, Kafka, ClickHouse и физическое выделение
сервисов вводятся только по указанным техническим триггерам.

## 2. Исходное состояние

### 2.1. Текущий стек

- Node.js 18+, CommonJS;
- Express 4;
- SQLite через `better-sqlite3`;
- WebSocket через `ws`;
- статические HTML-страницы и браузерный JavaScript без сборки;
- исторически данные страницы загружались полным `/api/state.js`; с этапа 3
  frontend использует контекстные screen DTO API v1;
- агрегаты считаются в `shared/core.js` на массивах;
- схема создаётся командами `CREATE TABLE IF NOT EXISTS` при запуске;
- автоматических тестов, миграций и CI нет.

### 2.2. Существующие рабочие сценарии

- регистрация и вход ученика/репетитора;
- приглашение в индивидуальную привязку или группу;
- создание группы и занятия;
- добавление ссылок и задач в занятие;
- решение, автопроверка и ручная проверка;
- живой просмотр черновика ученика;
- базовая статистика и настройки уведомлений;
- импорт задач JSON.

### 2.3. Принцип миграции

Нельзя одновременно менять runtime, БД, API и frontend. Используется подход
Strangler Fig:

1. зафиксировать текущее поведение тестами;
2. выделить границы модулей без изменения поведения;
3. заменить инфраструктуру за существующими интерфейсами;
4. вводить API v1 по одному экрану;
5. реализовывать функции на новом ядре;
6. удалять legacy только после телеметрии и периода совместной работы.

## 3. Целевая структура репозитория стартовой версии

```text
apps/
  web/                    # frontend/BFF
  api/                    # HTTP API и WebSocket bootstrap
  worker/                 # outbox, уведомления, фоновые задания
packages/
  contracts/              # OpenAPI types, event schemas, DTO
  domain/                 # чистые доменные правила и автоматы
  db/                     # schema, migrations, repositories
  auth/                   # identity и policy checks
  observability/          # logging, metrics, tracing
  config/                 # валидированная конфигурация
modules/
  identity/
  organizations/
  relationships/
  scheduling/
  learning/
  content/
  assessment/
  notifications/
  billing/
  analytics/
  audit/
tests/
  integration/
  e2e/
  contract/
infra/
  compose/
  terraform/
```

На первых шагах физический перенос файлов не обязателен. Сначала создаются
интерфейсы и тесты; перемещение выполняется небольшими коммитами без смешения с
изменением поведения.

## 4. Общие правила выполнения

### 4.1. Definition of Done каждой задачи

Задача завершена, когда:

- реализация и миграция данных готовы;
- добавлены unit/integration/e2e тесты соответствующего уровня;
- API/событие документировано и проверяется контрактом;
- права проверяются на сервере;
- логирование не содержит персональных данных и секретов;
- есть метрики для новой фоновой или критичной операции;
- предусмотрены rollback и повтор операции;
- обновлены `docs/` и связанные записи `brain/`;
- удалён либо зарегистрирован технический долг;
- CI проходит полностью.

### 4.2. Правила совместимости

- изменения БД выполняются по expand/migrate/contract;
- удаление столбца или endpoint — отдельный релиз после deprecation;
- новые команды имеют idempotency key там, где возможен повтор;
- DTO не совпадают автоматически с таблицами БД;
- события только добавляют совместимые поля внутри версии;
- feature flag имеет владельца, дату удаления и безопасное значение по
  умолчанию.

### Результат этапа 3 — 2026-08-09

- `docs/openapi.v1.yaml` является контрактом API 3.1, а
  `packages/api-client` генерируется из него;
- 16 страниц переведены на `/api/v1/screens/:screen.js`; legacy endpoint оставлен
  только на переходный период для совместимости и самим frontend не вызывается;
- публичные списки используют непрозрачный cursor, ограничение размера, фильтры
  и сортировку; ошибки API v1 возвращаются как `application/problem+json`;
- доступные create/accept/publish-команды требуют `Idempotency-Key` и сохраняют

  использовать тот же контракт;
- чтение занятия отдаёт versioned ETag, изменение требует `If-Match` и отклоняет
  потерянное обновление кодами 428/412;
- четыре PostgreSQL read-модели обновляются синхронными триггерами; команда
  `npm run db:read-models:rebuild` пересобирает и сверяет их с фактами;
- contract/integration/E2E тесты подтверждают отсутствие ответов и обращений
  frontend к legacy snapshot;
- при 100 запросах и concurrency 10 локальный p95 экранного чтения — 60,97 мс,
  payload login-screen — 2 614 байт против 44 681 байта legacy (−94,1%).

### Критерий выхода этапа 3

- frontend не использует `/api/state.js`;
- эталонные ответы отсутствуют во всех публичных DTO;
- payload экранов ограничен их контекстом;
- API описан OpenAPI и покрыт contract tests;
- p95 чтения ≤ 300 мс при десятикратной стартовой нагрузке.

## 16. Этап 11 — масштабирование realtime и аналитики

Этап выполняется по метрикам, а не заранее.

### 11.1. Realtime

Триггеры: более одного API/realtime-инстанса, более 500 одновременных сокетов,
недопустимые паузы при релизе или память rooms становится проблемой.

- [ ] `T11-001` Выделить stateless Realtime Gateway.
- [ ] `T11-002` Redis для presence и межинстансной доставки.
- [ ] `T11-003` Sequence number и resume from last acknowledged event.
- [ ] `T11-004` Connection/rate limits и backpressure.
- [ ] `T11-005` Нагрузочный тест с двукратным ожидаемым пиком.

### 11.2. Kafka

Триггеры: несколько независимых consumers одного потока, длительный replay,
backlog outbox влияет на API, поток событий устойчиво требует отдельного
масштабирования.

- [ ] `T11-010` Managed Kafka/KRaft-кластер и Schema Registry.
- [ ] `T11-011` Outbox relay публикует существующие event contracts.
- [ ] `T11-012` Partition key по aggregate ordering.
- [ ] `T11-013` Idempotent consumers, retry topics и DLQ.
- [ ] `T11-014` Consumer lag alerts и replay runbook.
- [ ] `T11-015` Parallel run и сверка PostgreSQL-handler/Kafka-handler.

### 11.3. Аналитика

Триггер ClickHouse: отчёты нагружают OLTP, объём событий/истории делает
PostgreSQL неэкономичным, необходимы большие многомерные срезы.

- [ ] `T11-020` Версионированная аналитическая схема событий.
- [ ] `T11-021` Псевдонимизация идентификаторов.
- [ ] `T11-022` ClickHouse ingestion и reconciliation.
- [ ] `T11-023` Формальный каталог метрик.
- [ ] `T11-024` Rebuild аналитических проекций.

### Критерий выхода этапа 11

- отказ Redis/Kafka/ClickHouse не уничтожает первичные данные;
- read-модели можно восстановить;
- нагрузочные SLO соблюдаются с запасом;
- каждый новый компонент имеет backup/restore либо rebuild-процедуру.

## 19. Артефакты управления реализацией

нагрузки. Выполненные пункты отмечаются здесь только после прохождения критерия
выхода, а не после написания кода.
