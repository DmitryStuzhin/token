# Архитектура arcs.studio

Разобрано из четырёх собранных экранов: главная, аккаунт, д/з, статистика.

## Что диктуют экраны

Четыре роли, а не одна. Ученик — это собранные страницы. Репетитор — проверка д/з, ведение занятий, заметки. Родитель — чтение прогресса ребёнка и оплата. Админ — привязка ученика к репетитору, абонементы, банк задач. Всё это один продукт с общей базой, но четыре разных набора прав.

Ключевая сущность — **Enrollment**: связка ученик ↔ репетитор ↔ предмет. Через неё висят занятия и домашние задания. Меняет её только админ, история привязок сохраняется — иначе при смене репетитора потеряется вся статистика ученика.

Статистика — **производные данные**. `TopicMastery`, `DailyActivity`, серия дней, KPI на главной пересчитываются из первичных фактов (решённые задачи, проверенные работы, проведённые занятия). Их нельзя считать на лету при каждом открытии главной — на графике пробников и хитмапе за 4 недели это будут десятки агрегирующих запросов на страницу.

## Три варианта

### A — модульный монолит
Одно Next.js-приложение, модули внутри, одна БД. Роли определяют, что показать.

Плюсы: одна кодовая база, один деплой, транзакции внутри одной БД, MVP за недели.
Минусы: пересчёт статистики нагружает тот же процесс; фоновые задачи (напоминания, дедлайны, списание абонемента) всё равно придётся выносить в отдельный процесс.
Когда: до ~1000 учеников, команда 1–3 человека, продукт ещё меняется каждую неделю.

### B — SPA + API + воркер
Фронт отдельно, API отдельно, фоновые задачи в очереди. Статистика читается из материализованных витрин.

Плюсы: релизы независимы, тяжёлые пересчёты не тормозят интерфейс, один API обслужит будущее мобильное приложение, админка — отдельное приложение с жёсткими правами.
Минусы: два-три репозитория, нужен контракт API, очередь — ещё один компонент в проде.
Когда: 1000–20000 учеников, команда 3–8 человек.

### C — сервисы и шина событий
Домены разнесены по сервисам, связь через события, у аналитики своя read-model.

Плюсы: изоляция доменов, аналитика масштабируется отдельно, история событий даёт аудит и возможность пересчитать агрегаты заново.
Минусы: eventual consistency, инфраструктуры больше, чем продукта, отладка через несколько сервисов.
Когда: десятки тысяч учеников, команда от 8 человек, жёсткие требования к аптайму.

## Рекомендация на старте: вариант A

Исходные данные: ~40 одновременных пользователей (ученики + репетиторы), плюс родители.

40 одновременных — это очень мало. В пике (вечер, 16:00–21:00, когда идут занятия) это десятки запросов в секунду, а не тысячи. Такую нагрузку держит один сервер 2 vCPU / 4 GB с большим запасом. Варианты B и C решают проблемы, которых на этих числах не существует, а платить за них придётся сразу — вторым репозиторием, контрактом API, отдельной инфраструктурой очереди.

Узкое место здесь не количество пользователей, а **количество запросов на одну страницу**. Страница статистики в текущем виде — это график пробников, шесть тем, хитмап за 28 дней, кольцо посещаемости и таблица работ. Если считать это на лету агрегатами по всей истории, страница будет открываться секунду даже при одном пользователе. Отсюда таблицы-агрегаты, а не более сложная архитектура.

### Конкретный стек

| Слой | Выбор | Почему |
|---|---|---|
| Приложение | Next.js (App Router) + TypeScript | один процесс, SSR, серверные экшены вместо отдельного API |
| БД | PostgreSQL + Prisma | реляционная модель, миграции, транзакции |
| Очередь и cron | **pg-boss** (очередь поверх Postgres) | на этих объёмах Redis не нужен — минус компонент в проде |
| Файлы | S3-совместимое хранилище | решения, скриншоты, материалы |
| Уведомления | Telegram Bot + SMTP | Telegram первым: он уже есть в профиле |
| Хостинг | один VPS с Docker Compose, либо Vercel + managed Postgres | |

Отдельно стоит подчеркнуть: **Redis на старте не нужен**. Он в схеме варианта A нарисован, но при 40 пользователях кэш ни на что не влияет, а очередь прекрасно живёт в Postgres через pg-boss. Добавите, когда появится реальная причина.

### Два шва под будущий переход в B

1. Логику домена держать отдельно от роутов и React-компонентов — не размазывать SQL по страницам.
2. Фоновые задачи с первого дня писать как задачи очереди, даже если очередь пока в том же процессе. Напоминание за час, простановка «просрочено» по `due_at`, пересчёт статистики, списание абонемента — четыре задачи по расписанию есть уже в MVP.

Тогда переход A → B — это вынести API и воркер, а не переписать домен. C не понадобится ещё очень долго.

## Родительский аккаунт

Идея хорошая, и по деньгам скорее всего необходимая: платит обычно родитель, а не одиннадцатиклассник. Но реализовать её «полем `parent_email` в профиле ученика» нельзя — родитель это полноценная роль.

### Guardian, а не поле в профиле

Связь родитель ↔ ребёнок — **отдельная таблица N—N**: у ребёнка бывает двое родителей, у родителя — несколько детей в системе. Плюс статус подтверждения, чтобы никто не подписался на чужого ребёнка по одному знанию email.

```
Guardian
  parent_user_id  → User (role = parent)
  student_id      → StudentProfile
  родство         — мама / папа / опекун
  статус          — приглашён | подтверждён | отозван
  доступ          — только чтение
  is_payer        — этот родитель платит
```

### Плательщик — отдельная ссылка

Из этого следует правка в биллинге: у `Subscription` появляется `payer_user_id` отдельно от `student_id`. Учится ребёнок, платит родитель, а иногда взрослый ученик платит сам. Если этого не заложить сразу, потом придётся переписывать всю оплату и историю платежей.

### Что родитель видит, а что нет

Родитель — **только чтение**, без единого исключения. Он не сдаёт д/з, не пишет ответы, не отменяет занятия за ребёнка.

Видит: расписание и ближайшее занятие, посещаемость, статусы и оценки д/з, статистику и динамику баллов, абонемент и историю платежей.

Не видит: содержимое решений ребёнка (это его рабочее пространство) и внутренние заметки репетитора. Поэтому у `LessonNote` появляется поле **видимости**: `ученик | родитель | только свои`. Репетитору нужно место, где он пишет «тяжело идёт, но давит родитель» — и это не должно попасть родителю в кабинет.

Ученик должен видеть, что родитель подключён — строкой в профиле. Скрытая слежка ломает доверие подростка к продукту, а он основной пользователь.

### Уведомления родителю — другие, чем ученику

У родителя свой `NotificationPref`. Ему не нужен поток «задача решена». Ему нужно: сводка раз в неделю, ребёнок пропустил занятие, д/з просрочено, списание через три дня.

### Экраны

Кабинет родителя — это существующая главная страница ученика, но read-only, без кнопок действий, плюс блок оплаты и переключатель детей, если их несколько. Компоненты переиспользуются почти целиком.

### Как не размазать права по коду

Одна функция на весь проект, отвечающая на вопрос «каких учеников видит этот пользователь»:

- ученик → сам себя
- репетитор → своих через `Enrollment`
- родитель → своих детей через `Guardian` со статусом «подтверждён»
- админ → всех

Все запросы к данным ученика идут через неё. Иначе проверки прав расползутся по страницам и однажды родитель увидит чужого ребёнка.

### Порядок

Родителя лучше не делать в первой итерации, но **`Guardian` и `payer_user_id` заложить в схему БД сразу** — это пять полей, а миграция биллинга задним числом стоит дорого.

## Занятие как живая сессия

Схема: `lesson-session.excalidraw`.

### Ссылки — таблица, а не поля

К занятию прикрепляется несколько ссылок разных типов: созвон (Zoom, Телемост), доска (Miro, Excalidraw), материалы. Не заводите `zoom_url` и `board_url` полями — заводите `LessonLink` с типом. Завтра появится ещё один сервис, и колонки закончатся. Кнопка «Подключиться» на главной = первая ссылка типа «созвон».

### Одна сущность для задачи на занятии и в д/з

Это главное решение. Задача, выданная на занятии, и задача из домашки — **это один и тот же `TaskAttempt`**, отличающийся полем `контекст: занятие | д/з | пробник`.

Если сделать их разными таблицами, статистика раздвоится: «№5 решался 20 часов» придётся собирать из двух несводимых источников, а проценты правильности начнут расходиться между экранами. Прежние `AssignmentTask` и `Submission` схлопываются в `TaskAttempt`, `Assignment` остаётся как пакет д/з.

```
TaskAttempt
  task_id · student_id
  контекст          — занятие | д/з | пробник
  lesson_id / assignment_id   — откуда пришла
  код в редакторе   — черновик ученика
  ответ · попыток · is_correct · верно_с_первой_попытки
  active_seconds    — чистое время
  статус · started_at · submitted_at
```

`верно_с_первой_попытки` стоит завести сразу: это честнее общего процента и полезнее для репетитора.

### Наблюдение за решением

Комната на занятие (`lesson:{id}`) по WebSocket. Ученик шлёт снапшот редактора раз в 2–3 секунды, сервер транслирует репетитору. Присутствие, «открыл задание», «ответил» — туда же.

**Не берите CRDT (Yjs) на старте.** Совместное редактирование нужно, когда оба правят один документ. Здесь поток односторонний: ученик пишет, репетитор смотрит. Периодического снапшота достаточно, и это на порядок проще.

### Автопроверка — без песочницы

Важное упрощение: проверяется **введённый ответ**, а не выполнение программы. Редактор кода — черновик ученика. Значит на старте не нужен изолированный запуск кода: ни контейнеров, ни лимитов CPU и памяти, ни защиты от бесконечных циклов.

У `Task` появляется `автопроверка: да|нет`, `тип ответа` (число / строка / множество) и правило сверки (регистр, пробелы, допуск). Задания вроде №27, где нужен сам код, идут репетитору в `Review`.

Автотесты кода — отдельный большой проект. Позже и только если реально понадобится.

### Учёт времени — здесь легко ошибиться

«№5 решался 20 часов» должно считаться **из активного времени**, а не из разницы «открыл — ответил». Иначе забытая на ночь вкладка даст 14 часов на одну задачу и испортит всю статистику.

- heartbeat раз в 15–30 секунд, пока вкладка в фокусе;
- пауза после ~2 минут без ввода;
- потолок времени на одну задачу.

События пишутся в `AttemptEvent` — из них же собирается лента для репетитора («открыл №17, печатает 4 минуты»).

### Новый агрегат под сводку

`TaskNumberStats` (student_id, ege_number, период) — попыток, верных, процент, суммарное и среднее время. Именно он отдаёт «№5: 20 ч, 77%» в недельной и месячной сводке и наполняет реальными данными блок «Средний результат по номерам заданий ЕГЭ» на странице статистики.

В сводке лучше показывать три числа вместе: суммарное время, процент и **среднее время на задачу**. 20 часов и 77% сами по себе не говорят, стало лучше или хуже; среднее время на задачу — говорит.

### Что это меняет в рекомендации

Вариант A остаётся, но с одной поправкой: нужен **долгоживущий процесс с WebSocket**. Значит VPS с обычным Node-процессом, а не serverless-хостинг, где сокеты живут плохо. Это ровно тот случай, когда выбор «VPS или Vercel» решается фичей, а не вкусом.

## Масштабирование вширь

Три вещи, которые дороже всего добавлять задним числом. Все три заложены сразу.

### Предмет — данные, а не код

Номера заданий, максимум баллов за каждое и шкала перевода первичного балла в тестовый
лежат в `subject.exam`:

```
Subject
  id · name · short
  exam.parts[]  — [{ number, maxPoints, topicId }]
  exam.scale[]  — первичный балл → тестовый
```

Ни одна функция статистики не знает про «27 заданий ЕГЭ по информатике»: покрытие банка,
сводка по номерам и пересчёт баллов пробника собираются из `parts` и `scale`. В прототипе
два предмета с разными сетками — информатика (27 заданий) и профильная математика (18) —
и обе работают через один код. Добавить физику = добавить объект в `subjects`.

Второе следствие: у ученика несколько привязок, по одной на предмет. Поэтому почти все
выборки принимают необязательный `subjectId`: без него — по всем предметам, с ним — по
одному. Переключатель предмета в интерфейсе строится из данных ученика и появляется сам,
когда предметов становится больше одного.

### Группы

```
Group        — tutor_id, subject_id, название, уровень, расписание, вместимость, статус
GroupMember  — group_id, student_id, joined_at, статус, источник
```

Занятие и домашнее задание адресуются **либо привязке, либо группе**: у `Lesson` и
`Assignment` есть и `enrollmentId`, и `groupId`, заполнен ровно один.

Ключевое решение: **группа — контейнер, а не владелец статистики**. Групповое задание —
одна запись, но попытки (`TaskAttempt`) создаются на каждого участника, и посещаемость
пишется построчно в `LessonAttendance`. Поэтому:

- ученик может одновременно быть в группе и заниматься индивидуально, и цифры не задвоятся;
- «сдали 3 из 5» по группе считается из тех же попыток, что и личная статистика;
- при вступлении в группу уже выданные групповые задания разворачиваются на новичка.

Если бы статистика хранилась на группе, пришлось бы держать два несводимых источника —
ровно та же ошибка, что и с разделением задач занятия и д/з.

### Приглашения

Привязка создаётся не админом, а по ссылке:

```
Invite
  code · kind: enrollment | group | guardian
  tutor_id · subject_id · group_id · student_id
  expires_at · max_uses · used_count · статус
```

Одна таблица закрывает три сценария — индивидуальные занятия, вступление в группу и
доступ родителя. Принятие создаёт `Enrollment` или `GroupMember` и увеличивает счётчик
переходов. Проверяется: срок, лимит переходов, отзыв, вместимость группы и повторное
вступление. Админ видит все ссылки и может отозвать любую, но в обычном потоке не участвует.

## Порядок работ

1. Схема БД и миграции — блоки «Люди и доступ» + «Учебный процесс» из доменной модели (включая `Guardian` и `payer_user_id`, даже если родитель ещё не делается).
2. Вход и роли, привязка ученика к репетитору (минимальная админка).
3. Занятия: расписание, статусы, ссылка на встречу → оживает главная.
4. Банк задач и `TaskAttempt`: выдача, решение, автопроверка → оживает страница д/з.
   Ссылки к занятию (`LessonLink`) — сюда же, они дешёвые.
5. Пересчёт агрегатов по событиям, включая `TaskNumberStats` → оживает статистика.
6. Живая сессия: WebSocket-комната, снапшоты редактора, лента репетитора.
7. Абонементы и платежи.
8. Уведомления (Telegram первым — он в профиле уже есть).
9. Группы: `Group`, `GroupMember`, групповые занятия и задания, `LessonAttendance`.
10. Приглашения: выпуск ссылки репетитором, приём, разворачивание групповых заданий.
11. Кабинет родителя: приглашение, подтверждение, read-only экраны, недельная сводка.

## Про даты в макетах

Числа на страницах декоративные и местами не сходятся: профиль говорит «с марта 2025» и экзамен 1 июня 2027, а обратный отсчёт «298 дней» соответствует лету 2026. При подключении данных отсчёт считается от реальной `Goal.дата_экзамена`.
