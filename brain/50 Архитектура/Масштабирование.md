# Масштабирование

> Где сейчас запас и что упрётся первым.

Целевой масштаб изменён с десятков пользователей на массовую платформу.
Полный план: [[ADR-010 Целевая событийная платформа]] и
`docs/ТЕХНИЧЕСКОЕ ЗАДАНИЕ.md`.

## Заложено вширь

| Что | Как |
|---|---|
| Новый предмет | запись в `subjects` с сеткой — [[ADR-003 Предмет как данные]] |
| Новый ученик | сам по [[Invite|ссылке]] |
| Группы | [[Group]] как контейнер, статистика по ученикам |
| Новые задачи | импорт JSON в [[Task]] |

## Что упрётся первым

1. **Пересчёт агрегатов на каждый запрос.** Лечится материализованными
   представлениями; сигнатуры функций уже под это подобраны.
2. **Полные state-read запросы.** PostgreSQL уже снимает ограничение одного
   SQLite-писателя; следующий предел — размер snapshot и стоимость сборки графа.
3. **WebSocket в памяти одного процесса.** Комнаты живут в `Map`.
   При нескольких процессах понадобится общая шина.
4. **Отсутствие фоновых задач.** Напоминания и «просрочено» сейчас
   считаются при чтении, а не по расписанию.

## Реализованный фундамент

Production PostgreSQL, пул соединений, нормализованная схема, UUIDv7,
управляемые миграции и ETL SQLite → PostgreSQL готовы. Kafka/Redis/ClickHouse не
подключены преждевременно: таблица outbox и границы модулей создают точки
подключения, когда метрики подтвердят необходимость.

## Порядок действий при росте

Вынести фоновые задачи → материализовать агрегаты → PostgreSQL →
разделить процессы. Это путь «вариант A → вариант B» из `docs/ARCHITECTURE.md`.

Этот путь сохраняется как миграционная последовательность, но целевое состояние
теперь включает PostgreSQL, Kafka, Redis, объектное хранилище и отдельный
аналитический контур. Компоненты выделяются по доменным границам и профилю
нагрузки, а не механически по таблицам.
