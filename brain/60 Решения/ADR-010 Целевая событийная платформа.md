# ADR-010 · Целевая событийная платформа

## Контекст

На старте продукт обслуживает не более 200 пользователей, но должен иметь путь
к массовой платформе с живыми занятиями, платежами, уведомлениями, большим
банком контента и тяжёлой аналитикой. [[ADR-001 Один процесс вместо микросервисов]]
остаётся разумным для запуска, но не описывает целевое состояние роста.

## Решение

Запускать модульный монолит с PostgreSQL и transactional outbox. Развивать
систему по доменным границам. Redis вводить для фоновых задач, rate limiting и
горизонтального realtime; Kafka — при подтверждённой событийной нагрузке и
нескольких независимых consumers; S3 — с появлением файлов; ClickHouse — при
объёме аналитики, который перестаёт эффективно обслуживать PostgreSQL.

## Важная граница

Решение прямо запрещает разворачивать сложную распределённую платформу только
ради будущего масштаба. Сначала вводятся контракты, владение данными, outbox и
наблюдаемость; физически выделяются только компоненты с подтверждённым
самостоятельным профилем нагрузки, безопасности или отказа.

## Чем платим

Операционной сложностью, eventual consistency read-моделей, необходимостью
идемпотентности, Schema Registry, DLQ, трассировки и отдельной платформенной
экспертизы.
